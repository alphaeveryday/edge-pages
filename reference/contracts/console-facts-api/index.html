    Super Admin Console — facts API¶

    슈퍼 어드민 콘솔의 규칙 엔진이 읽는 사실 계약이다. 판정 규칙 자체는 이 문서 밖이다 — 룰은 순수 함수이고 이 계약은 그 입력만 정한다. 배치 결정의 근거는 ADR-0050.

    착지 현황 — 이 문서는 dev 에 있는 것만 적는다¶

    정본은 dev 다. 축은 조각별로 하나씩 붙고, 그 축의 절은 그 조각과 함께 이 문서에 들어온다. 표에 없는 것은 아직 이 응답에 없다.

    조각 무엇 dev
    조회 창 어느 하루를 볼지 고르고 무엇을 봤는지 되돌려준다(meta) ✅
    런 축 runs[] ⏭
    계획 결손 슬롯 런 행이 없는 슬롯을 런 축에 싣는다 ⏭
    작업 축 tasks[] ⏭
    데이터셋 축 datasets[] (작업에서 파생) ⏭
    산출 축 outputs[] + 기준선(중앙값) ⏭
    경계 축 boundary ⏭

    엔드포인트¶

    GET /api/v1/console/facts[?date=YYYY-MM-DD]

    운영자 인증이 필요하다(AdminAuthFilter). 응답은 기존 콘솔 API 와 같은 봉투(result)를 쓰고, 필드명은 UI 타입과 같은 camelCase 다.

    {
  "result": {
    "meta": {
      "db": "2026-08-03T07:20:34Z",   // DB 시계 — 화면의 "언제 기준인가"
      "today": "2026-08-03"           // 실제로 본 날
    }
  }
}

    조회 창¶

    창은 하루다. date 를 생략하면 서버가 고르고, 무엇을 골랐는지 meta.today 로 되돌려준다 — 화면이 요청한 날짜를 그대로 그리면 서버가 다른 날을 골랐을 때 거짓말이 된다.

    어느 날을 고르나¶

    1. 런이 있던 마지막 날
    2. 계획만 있고 런 행이 없던 마지막 날(ops_reconciliation_issue PLANNER_MISSING)
    3. 둘 중 뒤쪽. 둘 다 없으면(원장이 빔) DB 시계의 KST 오늘

    ⚠️ 2번을 빼면 안 된다. 런이 하루도 안 뜬 날이 조회 후보에서 사라지는데, 그날이 바로 콘솔이 열려야 하는 날이다.

    런이 어느 날에 속하나¶

    COALESCE(r.trading_date, (r.created_at AT TIME ZONE 'Asia/Seoul')::date)

    ⚠️ trading_date 로 단순화하지 마라 — 비거래일 런은 그 컬럼이 NULL 이라 통째로 새어 나간다. 이 식을 쓰는 자리가 앞으로 여럿이 된다(조회 창 · 작업 조인 · 최신 날짜). 한 자리라도 다르게 쓰면 그 런이 창에는 들어오는데 최신 날짜에는 안 잡혀 기본 화면에서 사라진다.

    ⚠️ 날짜 캐스트는 존을 항상 명시한다. 생략하면 세션 TimeZone(=JVM 기본값)을 타서 로컬(KST) 에서는 맞고 운영(UTC)에서만 하루가 밀린다 — 통합 테스트가 못 보는 자리가 된다.

    요청 날짜 검사 — 셋 다 400¶

    입력 왜
    형식 오류(2026-8-3) 아래 계층에서 터지면 500 으로 위장돼 운영자가 원인을 못 찾는다
    확장 연도(+999999999-12-31) SourceService 와 같은 규약
    미래 날짜 아직 오지 않은 날의 사실은 실측 0 이 아니라 "아직" 인데, 이 응답에 그 둘을 가르는 자리가 없다

    ⚠️ 미래의 상한은 KST 오늘이지 원장의 최신 거래일이 아니다. 최신 거래일로 자르면 계획이 통째로 안 돈 날(런 0건 + PLANNER_MISSING)을 못 열게 되는데, 그날이 콘솔이 열려야 하는 날이다 — 게이트가 사고를 숨기는 방향으로 서면 안 된다.

    원장에서 오는 미래도 같은 이유로 막는다: 미래 거래일 런이나 미래 슬롯 키가 하나라도 있으면 기본 조회가 오지 않은 날로 뛴다. 그래서 후보 조회에 상한을 KST 오늘로 건다.

    부재를 싣는 규약¶

    이 응답의 핵심은 값이 아니라 부재의 종류다. 셋을 끝까지 가른다:

    뜻 어떻게
    실측 0 0
    집계 없음 · 관측 불가 null
    계측 없음 키 자체가 없다

    []·0·"" 으로 메우지 않는다 — 화면이 "괜찮다"로 그린다. 표시 문자열도 만들지 않는다 (포맷은 UI 소관 — SourceReportResponse 가 이미 지키는 규약).

    ⚠️ 그래서 아직 안 붙은 축은 빈 배열이 아니라 키가 없다. runs: [] 로 내려가면 규칙 층이 "축은 왔는데 비었다"로 읽어 못 돎 대신 "평가됨 · 위반 0" 을 세운다 — 계측 공백이 정상으로 뒤집힌다. 축을 하나씩 더하는 지금은 그 구분이 곧 진행 상태의 정본이다.

    ⚠️ 클래스 단위 @JsonInclude(NON_NULL) 을 걸지 않는 이유가 이것이다 — 위에 걸면 "집계 없음(null)"이 조용히 "계측 없음(필드 부재)"으로 바뀌어, 콘솔이 없애려는 칸 혼동을 서버가 다시 만든다. 필요한 필드에만 붙인다.

    성능에 대해 지금 하지 않는 것¶

    날짜 후보 조회에 하한(lookback)을 두지 않는다. 한 번 뒀다가 되돌렸다 — 90일 창은 파이프라인이 그보다 오래 멈췄다 재개한 날 원장이 아는 마지막 날을 창 밖으로 밀어낸다 — run_latest 도 계획 결손일도 안 잡혀 기본 조회가 KST 오늘로 떨어지고, 화면은 사고 난 그날 대신 빈 오늘을 연다. 안 해도 될 성능 대비로 계약을 깎은 것이었다.

    규모가 그 대비를 요구하지 않는다: ops_pipeline_run 은 레인 4개 × 하루 1~3슬롯이라 연 수천 행이고, 날짜 조회는 그중 DISTINCT 날짜(운영 일수)만 낸다. 느려지면 인덱스가 먼저다.
